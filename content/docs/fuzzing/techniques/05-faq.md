# FAQ（ファジング版・よくある質問） {#faq-fuzzily-asked-questions}

## ファザーはクラッシュを報告しているのに、ファザーの外で SUT にそのテストケースを与えると、クラッシュしません。何が起きているのですか？

考えられる理由はいくつかあります。


- SUT の動作が非決定的である。
- SUT がグローバルな状態に依存している（たとえば、ディスクの読み書きや、メモリ上のシングルトンを使っている）。
- システムのメモリが足りなくなり、プロセスが強制終了されたためにクラッシュしている。これは Linux では通常、シグナル 6 で示されます。`dmesg` の出力を確認して、メモリ不足に関する記録がないかを見ることもおすすめします。 


## ファジングはいつやめればよいですか？

この問いに答えるのはとても難しいです。現在のファザーで使える指標は、実質的にコードカバレッジだけです。コードカバレッジは、ファザーがバグを見つける効率を測るための代わりの指標です。

ただし、今あるのはコードカバレッジだけだと認めたうえで、実用的な答えを言えば、ファザーが数時間にわたって新しいテストケースを見つけなくなったらファジングをやめます。これは、ファザーのカバレッジが増えなくなったと言うのと同じです。

ファジングに関する学術論文の多くは 24 時間のキャンペーンを実行していますが（[Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700) の Table 1 と section 6 を参照）、特定の期間についての決まった推奨はありません。ファザーを長く動かすほうが有益なこともあります。24 時間より長い期間を試して、ファジングキャンペーンを観察してください。

実行回数の合計は、時間よりも重要な指標であることを、必ず心に留めておいてください。SUT の実行が遅いなら、ファジングを長く続けてください。特定の時間に盲目的にこだわってはいけません。

また、Trail of Bits での経験から、ファジングキャンペーンを複数回実行し、定期的にコーパスをリセットして、カバレッジが変わったかを確認することをおすすめします。こうすると、ファザーが、十分な情報を持つフィードバックがない、あるいはファザーの探索を適切に導くフィードバックがないために、プログラムの別の状態を探索するのに苦労しているときの助けになります。ファジングキャンペーンを再開すると、前回とは異なるプログラムの部分を、ランダムに探索することがあります。

## コーパスは非公開にすべきですか、公開すべきですか？

既定では、コーパスは非公開にしておくべきです。コーパスは貴重な資産で、作るには多くの労力がかかります。コーパスを手に入れた攻撃者は、脆弱性をより簡単に見つけられるかもしれません。

ただし、OpenSSL など多くのプロジェクトは、[コーパスを公開](https://github.com/openssl/fuzz-corpora/)することにしました。おそらく、セキュリティ研究者を支援するためです。また、CI でコーパスを使ってファジングするためのセットアップが簡単になります。

結論として、これはプロジェクトごとにリスクを評価して決めることです。まずはコーパスを非公開にしておき、いずれ公開することをおすすめします。

## ファザーが何も見つけません。ファジングの設定にバグがあることを示す兆候は何ですか？

ファジング中のコードカバレッジを確認してください。このファジングの章には、扱っているファザーごとにカバレッジを確認する方法のガイドがあります。

コードカバレッジの代わりの指標として、1 秒あたりの実行回数が使えます。
- 多すぎる場合（1 秒あたり 10⁶ 回超）は、重要なコードが実行されておらず、コードカバレッジが低い可能性が高いです。SUT が早い段階でエラーに当たり、そのまま正常に戻っているのかもしれません。
- 少なすぎる場合（100 回未満）は、対象の実行が遅すぎて、ファザーが興味深いテストケースを見つけられるほど速く進んでいないのかもしれません。

## ファジングキャンペーンの最中や後に起きたクラッシュのコアダンプを集めるには、どうすればよいですか？

Linux では、コアダンプに影響する主な設定が 2 つあります。1) プロセスごとにコアダンプを有効にする「core」の[リソース制限](https://man.archlinux.org/man/setrlimit.2)と、2) コアダンプの保存先や送信先を決める `sysctl` の設定 [`kernel.core-pattern`](https://docs.kernel.org/next/admin-guide/sysctl/kernel.html#core-pattern) です。
Bash シェルでは、`ulimit -c` でコアダンプの現在の制限を確認でき、`ulimit -c 0` で無効に、`ulimit -c unlimited` で有効にできます。リソース制限の既定値は、環境やオペレーティングシステム（サーバー用と、デスクトップ用のオペレーティングシステムなど）によって異なります。コアダンプを、現在の作業ディレクトリの `core` というファイルに保存するには、次のようにカーネルを設定します。

```shell
sysctl -w kernel.core_pattern=core
```

クラッシュするプログラムの実行のしかたによっては、それでもコアダンプのファイルが得られないことがあります。ファザーは、現在のプロセスのリソース制限を設定したり、シグナルハンドラを上書きしてコアダンプの作成を避けたりして、コアダンプの作成を妨げることがあります。コアダンプは作成に時間がかかることがあるため、ファザーはコアダンプを無効にします。ファザーは、クラッシュに遭遇したあとも、速やかにファジングを続けたいのです。

デバッグにコアダンプが必要な場合は、お使いのファザーのドキュメントで、コアダンプを再び有効にする方法を確認してください。リソース制限と `kernel.core_pattern` を必ず設定してください。

libFuzzer、AFL++、Hongfuzz については、次の指針に従ってください。

- **libFuzzer.** 既定では、libFuzzer はシグナルハンドラを登録してコアダンプを無効にします。コアダンプの書き出しを有効にするには、[ASan を有効にして]({{% relref "10-libfuzzer#addresssanitizer" %}})から、環境変数 `ASAN_OPTIONS=abort_on_error=1:disable_coredump=0` を設定する必要があります。これは、ASan が処理するクラッシュにしか効かないことに注意してください。[`abort`](https://man.archlinux.org/man/abort.3p) の呼び出しでは、この方法ではコアダンプが作成されません。
- **AFL++.** 環境変数 `AFL_DEBUG` を `1` に設定します（このオプションのソースコードは[こちら](https://github.com/AFLplusplus/AFLplusplus/blob/0c054f520eda67b7bb15f95ca58c028e9b68131f/src/afl-forkserver.c#L891)）。
- **Hongfuzz.** フラグ [`--rlimit_core`](https://github.com/google/honggfuzz/blob/348a47213919f14b9453e89a663b1515369bd9a2/docs/USAGE.md?plain=1#L170-L171) を大きな値に設定します。
