# ファジング

ファジングは、不正な形式のデータや予測できないデータをシステムに入力して、セキュリティ上の問題、バグ、システムの障害を検出する動的なテスト手法です。私たちは、これをテスト一式に含めるべき不可欠なツールだと考えています。

この Testing Handbook の章では、プロジェクトのファジングをすばやく始める方法を説明します。基本を押さえたあとで、より高度なファジング手法を掘り下げ、テストの構成を次の段階に引き上げる方法を示します。章の終わりまでに、適したファザーの選び方、ファジングのハーネスの書き方、その出力の読み方を身につけ、実際のプロジェクトに応用できるようになります。この章は、順を追って進められ、半日ほどで終えられます。

ファズテストの概念は 30 年以上前にさかのぼり、当時は UNIX のコマンドラインユーティリティの調査に使われていました([An empirical study of the reliability of UNIX utilities](https://dl.acm.org/doi/pdf/10.1145/96267.96279)を参照)。それ以来、ファジングは、完全にランダムな入力を生成するもの(ブラックボックスファジング)から、テスト対象のプログラムの実行中に集めたフィードバックにもとづいて入力を生成するもの(グレイボックスファジング)へと進化しました。これらのユーティリティは C で書かれているため、まず C/C++ プロジェクトのファジング方法から説明します。その前に、この章の想定読者と構成について、少し説明します。

## 想定読者と範囲 {#audience-and-scope}

このファジングの章は、テストハンドブック全体と同じく、開発者とセキュリティエンジニアの両方を対象にしています。読者は、各セクションで扱うプログラミング言語にすでに慣れていて、Bash、Git、cURL のような一般的な UNIX のツールに親しんでいることを前提とします。含まれている例を読み進めて実行するには、Debian、Ubuntu、またはほかの Linux の経験が必要です。

何よりもまず、テストハンドブックは、自分のコードをテストするエンジニアのためのものです。したがって、この章は、ソースコードを入手できるプロジェクトのファジングに焦点を当てています。 

ファジングの出発点を提供したいと考えていますが、無数のほかのガイドで繰り返し書かれてきた内容をなぞるのではなく、関連するドキュメントがあればそれを案内するようにしています。私たちの解説は、基本的な構成が動くようになったあと、どう続けるかに焦点を当てています。ファジングの構成の最初の版は、コードカバレッジの分析などの手法を使えば、たいてい簡単に改善できます。


## 構成 {#structure}

この章は、拡張できる構成にしました。言語(C/C++、Rust、Go など)ごとに、使えるファザーを列挙します。どのファザーを選ぶべきかを助言し、そのあとで、ファザーのインストール方法、ファズテストのコンパイル方法、ファザーの使い方を説明します。マルチコアでのファジングや、[サニタイザ](https://en.wikipedia.org/wiki/Code_sanitizer)への対応<!-- TODO link our sanitizer section in the future -->のような特別な機能がファザーにある場合は、そのあとに追加します。各ファザーのセクションは、実際の例と、さらに参考になる資料で締めくくります。

各言語のセクションは、その言語に固有の「テクニック」サブセクションで終わります。すべての言語とファザーに当てはまる手法は、章の最後にある[テクニック]({{% relref "/docs/fuzzing/techniques" %}})のセクションに載せています。この最後のセクションには、[FAQ]({{% relref "05-faq" %}})と、[ファジングの環境]({{% relref 04-env%}})に関する情報も含まれています。

## 用語 {#terminology}


* **SUT/ターゲット:** テスト対象のシステム(System Under Test、SUT)は、テストされているソフトウェアのことです。コマンドラインのプログラムのような単体のアプリケーションでも、ライブラリでもかまいません。
* **ファジング/ファザー:** ファズテスト(ファジング)は、無効なデータ、予期しないデータ、ランダムなデータを入力として SUT に与える、自動化されたソフトウェアのテスト手法です。ファジングのアルゴリズムを実装したプログラムを、ファザーと呼びます。
* **テストケース:** テストケースは、テストのハーネスに与える具体的な入力です。通常は、文字列かビット列です。テストの入力は、抽象構文木のような、より複雑な形式で符号化されることもあります。
* **(テスト/ファジングの)ハーネス:** ハーネスは、特定の SUT のテストの準備を担います。ハーネスはソフトウェアを包み、テストケースを実行できる状態になるように初期化します。ハーネスは、SUT をテスト環境に組み込みます。
* **libFuzzer のハーネス:** libFuzzer ライブラリと互換性のあるハーネスです。この用語は、`LLVMFuzzerTestOneInput` 関数を指します。
* **ファズテスト:** ファズテストは、ファジングのハーネスと SUT からなります。ハーネスと SUT を含むコンパイル済みのバイナリを、ファズテストと呼ぶこともあります。
* **ファジングキャンペーン:** ファジングキャンペーンは、ファザーの 1 回の実行です。ファザーがテストを始めたときに始まり、ファジングの処理が止まったときに終わります。
* **コーパス:** 変化していくテストケースの集合です。ファジングキャンペーンの間、新しいテストケースが見つかるにつれて、コーパスは通常、大きくなります。
* **シードコーパス:** ファジングキャンペーンは通常、テストケースの初期の集合を使って始めます。この集合を、シードコーパスとも呼びます。コーパスの各テストケースを、シードと呼びます。
* **ファジングエンジン/ランタイム:** ファジングエンジン/ランタイムは、ファジングの開始時に実行される、ファザーの一部です。ファジングの処理全体を取りまとめます。
* **計装:** プログラムを計装するとは、プログラムからデータを取り出したり、より安全で堅牢にしたりするために、機能には関わらない変更を加えることです。
* **コードカバレッジ:** プログラムのソースコードがどの程度実行されたかを測る指標です。

## ファジングの長所と短所 {#pros-and-cons-of-fuzzing}

ファジングには、手動のコード監査や単体テストなどのほかのテスト手法と比べて、いくつかの利点と限界があります。

|利点|欠点|
|--- |--- |
|**見落とされた脆弱性を見つけられる:** 入力空間を広くカバーするため、ファザーは、手動の確認では見つからなかったバグを見つけられます。|**複雑な入力が課題になる:** 複雑な入力(TLS のようなネットワークパケットやソースコードなど)を必要とするソフトウェアでは、コードカバレッジが高い効率的なファザーを開発するのに、大きな労力がかかります。|
|**自動化とスケーラビリティ:** ファザーは、いったん動き出せば、数時間から数か月にわたる長い期間、欠陥を探し続けられます。|**バグの検出が不完全:** ファジングは、すべてのバグを捕捉できるとは限りません。特に、プログラムをクラッシュさせないバグや、ごく特定の条件でしか起こらないバグは見逃しがちです。|
|**費用対効果が高い:** 最初の準備にコストはかかりますが、時間がたつにつれて、ファジングは手動のテストよりも費用対効果が高くなります。|**従来はメモリ破壊のバグが中心:** 従来のファジングは、Rust や Go のようなメモリ安全な言語では起こりえない、メモリ破壊によるプログラムのクラッシュを見つけることに集中していました。ただし、ファジングのコミュニティは、ロジックのバグの発見にも、少しずつ重心を移しています。|
|**メモリ破壊のバグを見つける実績のある手法:** ファジングは、メモリ管理に関連する何千ものバグを見つけてきました。メモリ安全でない言語には、欠かせないツールであることが実証されています。||
{.hide-empty-cells}

ソフトウェアパッケージをファジングするときの最初の手順は、パッケージ内のファジングする価値があるターゲットを見極めることです。ファジングは、特定のコード構造では特によく機能し、ほかの構造では手間がかかることがあるからです。たとえば、パーサーのファジングは簡単です。準備しやすく、バグが見つかる見込みも高いからです。プロジェクトが複雑なアプリケーションのロジックを実装していて、テストしにくい(つまり、まだ単体テストがない)場合は、静的解析ツール、きちんとした単体テスト、手動のコードレビューのほうが、大きな効果を得られるかもしれません。これらのテスト手法を取り入れたあとの次の一歩が、コードのファジングになるでしょう。

ファジングは、単体テストや静的解析と同じく、万能の解決策ではありません。現在、静的解析ツールや動的解析ツールとファジングを比較するセクションを準備しています。更新をお待ちください。 <!-- TODO: Link when comparision section is done! -->

典型的なファジングの構成を紹介する前に、まず、現在の標準的なファジングの戦略である、変異ベースの進化型ファジングを説明します。


## 標準のファジングアルゴリズムは変異ベースで進化型 {#the-default-fuzzing-algorithm-is-mutation-based-and-evolutionary}

元祖の [AFL](https://lcamtuf.coredump.cx/afl/) ファザーは、進化的アルゴリズムに着想を得たファジングアルゴリズムを採用していました。このアルゴリズムは、ファザーの事実上の標準のアルゴリズムです。

基本的な考え方は、テストケースの集団をコーパスの中に保つことです。コーパス内の各テストケースには、生物学の理論になぞらえて、ある適応度があります。適応度は、テストケースの適応度を表すカバレッジの指標を使って決められます。進化的アルゴリズムは、適応度の高いテストケースを選んで、変異を加え、子孫を作ります。変異させた新しいテストケースはそれぞれ実行され、適応度が割り当てられます。適応度の面で有益な子孫だけを生き残らせる、という考え方です。この進化の過程は、次のセクションでより詳しく説明します。


{{< customFigure "進化型のファザーを示す疑似コード" >}}
```Rust  {linenos=inline}
fn fuzz(corpus) {
  let bug_set = []; // We start with an empty set
  while let Some(test_case) = schedule(corpus) { // Now, we pick one test case after the other
    let offspring = mutate(test_case); // Each test case is mutated to create offspring
    let observations = execute(offspring); // New test cases are executed

    if (is_interesting(observations)) {
      corpus.append(offspring); // If the observations are interesting we keep the new test case
    }
    if (is_bug(observations)) {
      bug_set.append(offspring); // If the observations indicate that a bug occurred then we store the test case
    }
  }
  return bug_set; // The set of bugs is returned
}
```
{{< /customFigure >}}

**ファジングの入力:** 上の疑似コードは、ファジングキャンペーンの間に実行される手順を表しています。1 行目は、入力として初期のコーパスを想定していることを示しています。初期のコーパスは空でないことが必要です。また、関数の 1 行目で、空のバグ集合から始めています。ファジングキャンペーンの間、バグ集合は、バグを引き起こしたテストケースを集めます。

**`schedule(test_case)`:** 3 行目では、コーパスからテストケースを 1 つずつ選ぶことで、ファジングのループを始めます。`schedule` 関数は、最終的に何も返さないことで、ファジングキャンペーンを止めると決めます。たとえば、決まった回数の反復のあとに、そうなることがあります。

**`mutate(test_case)`:** 4 行目では、テストケースを変異させて子孫を作ります。変異は、さまざまな方法でテストケースを変えられます。テストの入力がバイト配列なら、一般的な変異の戦略には、バイト配列のビットの反転、バイト配列への新しいバイトの挿入、バイト配列の切り詰めがあります。

**`execute(test_case)`:** 5 行目では、観測結果を得るために、新しいテストケースを実行します。最も単純な観測結果は、変異させたテストケースの実行にかかった時間です。より複雑な観測結果には、SUT 内で実行されたコードの行が含まれることもあります。

**ファジングの出力:** 8 行目と 11 行目では、観測結果が、子孫の興味深い挙動を示している場合は、コーパスを、バグが観測された場合は、バグ集合を、それぞれ増やします。

言い換えると、バグを見つけるうえで前進を表すものがあれば、それをコーパスに追加します。進化的アルゴリズムになぞらえると、適応度の高い子孫を優遇するということです。従来、テストケースが興味深いかどうかは、コードカバレッジが増えるかどうかと一致していました。

ファジングキャンペーンが終わると、見つかったバグが返されます。


## ファザーの紹介 {#introduction-to-fuzzers}

どのファジングの構成も、計装されたテスト対象のシステム(SUT)、ファジングのハーネス、ファザーのランタイムからなります。計装用のランタイムが必要になることもあります。たとえば、省略可能な [AddressSanitizer]({{% relref 03-asan %}})(ASan)による計装は、[ヒープバッファオーバーフロー](https://en.wikipedia.org/wiki/Heap_overflow)のような[メモリ破壊のバグ](https://en.wikipedia.org/wiki/Memory_corruption)をより確実に検出するためのランタイムを追加します。次の図は、標準的なファジングの構成を示しています。

{{< resourceFigure "intro.svg" >}}
一般的なファジングの流れでは、開発者が SUT 用のハーネスを書きます。ファジングキャンペーンを始めると、ファザーのランタイムがランダムなテストケースを生成し、ハーネスに送ります。ハーネスは SUT を実行し、その結果、バグやクラッシュが見つかることがあります。ほとんどのファザーは SUT のコードを計装してランタイムを追加しますが、計装用のランタイムと、SUT に追加される計装は、一般には省略可能です。
{{< /resourceFigure >}}

**SUT(テスト対象のシステム):** テストしたいコードです。SUT のファジング用ビルドを作るには、アプリケーションのコードがどのようにコンパイルされ、リンクされるかを制御する必要があります。次の図は、この Testing Handbook の章全体で例として使う、ごく単純な SUT を示しています。

{{< customFigure "SUT の例" "html" >}}
{{< tabs "sut" >}}
{{< tab "C/C++" >}}
```C++
#include <stdlib.h>
#include <string.h>

void check_buf(char *buf, size_t buf_len) {
    if(buf_len > 0 && buf[0] == 'a') {
        if(buf_len > 1 && buf[1] == 'b') {
            if(buf_len > 2 && buf[2] == 'c') {
                abort();
            }
        }
    }
}

#ifndef NO_MAIN
int main() {
    char target[] = "123";
    size_t len = strlen(target);
    check_buf(target, len);
    return 0;
}
#endif // NO_MAIN
```
main.cc (C/C++): abort を引き起こすバグを含む SUT の例。`check_buf` 関数は、入力 "abc" で abort します。
{{< /tab >}}

{{< tab "Rust" >}}

```Rust
use std::process;

fn check_buf(buf: &[u8]) {

        if buf.len() > 1 && buf[1] == b'b' {
            if buf.len() > 2 && buf[2] == b'c' {
                process::abort();
            }
        }
    }
}

fn main() {
    let buffer: &[u8] = b"123";
    check_buf(buffer);
}
```
main.rs (Rust): abort を引き起こすバグを含むコードの例。`check_buf` 関数は、入力 "abc" で abort します。

**ハーネス:** ハーネスは、ファズテストのエントリポイントです。ファザーは、ランダムな、または慎重に変異させたデータで、この関数を呼び出します。ハーネスを書いて使うときのコツは、[ハーネスの書き方]({{% relref "/docs/fuzzing/techniques/01-writing-harnesses" %}})と、[実践的なハーネスの規則]({{% relref "/docs/fuzzing/techniques/01-writing-harnesses#practical-harness-rules" %}})を参照してください。



{{< customFigure "ハーネスの例" "html" >}}
{{< tabs "harness" >}}
{{< tab "C/C++" >}}
```C++
#include <stddef.h>
#include <stdint.h>
#include <stdlib.h>

void check_buf(char *buf, size_t buf_len);

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
  check_buf((char*) data, size); // Invoke the SUT; in our case that is the check_buf function
  return 0; // Return 0, which means that the test case was processed correctly
}
```
harness.cc (C/C++): ファザーのエントリポイント

事実上標準の libFuzzer の API は、LLVMFuzzerTestOneInput という名前です。この関数は、バイトバッファと長さを受け取り、0 を返します。戻り値の意味は、ファザーごとに決まっています。libFuzzer では、0 と -1 以外の値は予約されています。-1 を返すと、現在のテストケースをスキップし、コーパスへの追加を避けます。AFL++ は戻り値を無視します。LibAFL は、-2 が返されると、テストの入力をバグとして分類します。
{{< /tab >}}

{{< tab "Rust" >}}
```Rust
fn harness(data: &[u8]) {
    check_buf(data);
}
```
harness.rs (Rust): ファザーのエントリポイント

Rust のエコシステムには、ハーネスの関数シグネチャの標準がありません。汎用性を保つために、Rust のファジングのハーネスは、Rust の型 `&[u8]` のランダムなデータを持つバイト配列を受け取る、void の関数だと仮定します。
{{< /tab >}}

ハーネスを書くときには、多くの手法を活用できます。それらは、[ハーネスの書き方]({{% relref "docs/fuzzing/techniques/01-writing-harnesses" %}})のセクションで説明します。また、特定のコードをハーネスで実行することを禁じる[規則]({{% relref "docs/fuzzing/techniques/01-writing-harnesses#practical-harness-rules" %}})があることにも注意が必要です。

**ファザーのランタイム:** ファジングのループは、ここで実装されます。この部分は、ファザーの main 関数も提供します。ファジングのランタイムは、ファジングのオプションを解析し、ハーネスを実行し、フィードバックを集め、ファザーの状態を管理します。ランタイムは、libFuzzer や AFL++ など、使うファジングのプロジェクトが提供します。計装を通じてフィードバックを集めるために必要なランタイムは、すべてファザーのランタイムに実装されています。

**計装のランタイム:** [AddressSanitizer]({{% relref 03-asan %}})や [UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html) のような計装には、ランタイムが付いています。バグを確実に検出し、フィードバックを効率よく実装するには、ファザーがサニタイザと互換性を持っている必要があります。Go や Rust のようなメモリ安全な言語では、サニタイザが必要になる場面は少なくなります。

いま挙げた 2 つのサニタイザは、より多くのバグを見つけることを目的に、計装を導入するものだという点に注意してください。実行中にファザーへフィードバックを提供する、別の種類の計装(たとえば [SanitizerCoverage](https://clang.llvm.org/docs/SanitizerCoverage.html))もあります。フィードバックにもとづく計装のランタイムは、通常、ファザーのランタイムの一部です。

## 何をファジングするか {#what-to-fuzz}

ファジングは、どのような種類の問題を見つけられるでしょうか。

* クラッシュとパニック
    * メモリ破壊の問題: UAF、整数オーバーフロー、未定義動作、バッファオーバーフロー、メモリリークなど

* 不変条件の違反: ビジネスロジックのバグ
    * 状態の不変条件の違反: ステートフルなファジングが必要な性質

* 差分: 同じ機能の異なる実装どうしの相互テスト
    * プラットフォーム間の差分: 同じコードを異なるアーキテクチャでテストする
    * リグレッション: 同じコードの異なるバージョンの間
    * 実装間: 似た機能を実装している異なるライブラリやツールの間

* 壊れた論理的性質
    * 往復: `decode(encode(x)) == x`
    * 冪等性: `f(f(x)) == f(x)`
    * 単調性: `x < y → f(x) ≤ f(y)`
    * 単位元: `f(x, identity) == x`
    * 可換性: `f(x, y) == f(y, x)`
    * 結合性: `f(f(x, y), z) == f(x, f(y, z))`
