# 定数時間解析ツール

{{< math >}}
タイミング攻撃は、実行時間のばらつきを利用して秘密の情報を取り出すサイドチャネルです。

暗号プロトコルの弱点を探して理論上の安全性の保証を破ろうとする暗号解読とは違い、タイミング攻撃は、特定のプロトコルの実装上の欠陥を利用します。公開鍵暗号のような特定の暗号方式は、タイミング攻撃に対してより脆弱なことがありますが、この攻撃経路は、どの暗号実装にも影響しうるものです。

タイミング攻撃を緩和するには、実装を定数時間にする (暗号関数の実行時間が、入力にかかわらず一定であること) のがベストプラクティスです。実際には、**コードの経路とメモリアクセスが、秘密データに依存しないようにする**必要があります。すべてのタイミングの違いが悪用できるわけではありませんが、違いをすべてなくせば、実装の安全性を確保できます。実装が定数時間であることを確かめるために、暗号の実務者たちは、定数時間ではないコードを検出するさまざまなツールを開発してきました。  

この項目は 2 つの節に分かれています。
最初の節では、タイミング攻撃の[背景](#background)と具体的な[例](#example-modular-exponentiation-timing-attacks)を紹介します。
2 番目の節では、実装が定数時間かどうかを確かめるために実務者が使える、さまざまな[ツール](#constant-time-tooling)を取り上げ、4 つのクラスに分類します。それぞれに長所と限界があります。

## 背景 {#background}

暗号実装に対するタイミング攻撃は、1996 年に [Kocher](https://paulkocher.com/doc/TimingAttacks.pdf) が提唱しました\。その後、さまざまな研究者がこれらの攻撃を発展させてきました。特に、[Schindler](https://link.springer.com/content/pdf/10.1007/3-540-44499-8_8.pdf) は、特定の最適化を使った RSA 実装への攻撃を示しました。2003 年には Brumley と Boneh が [Remote Timing Attacks are Practical](https://www.usenix.org/legacy/events/sec03/tech/brumley/brumley.pdf) を発表し、OpenSSL から秘密鍵を取り出すことに成功しました。また、AES のような共通鍵暗号も、[Cache-timing attacks on AES](https://cr.yp.to/antiforgery/cachetiming-20050414.pdf) で示されたように、タイミング攻撃に対して脆弱なことがあります。  
最近では、耐量子計算機暗号のアルゴリズム Kyber の公式実装にタイミングの脆弱性が見つかり、[KyberSlash](https://eprint.iacr.org/2024/1049.pdf) と名付けられました。実装で見つかったタイミングの脆弱性は、[CWE-385](https://cwe.mitre.org/data/definitions/385.html) のカタログで追跡されています。  

一般に、タイミング攻撃を成立させるには、2 つの重要な前提条件を満たす必要があります。

1. 十分な回数の問い合わせができるオラクルにアクセスできること。  
2. 秘密と攻撃者が制御するデータの間に、タイミングの依存関係があること

必要な問い合わせの回数は、タイミングの漏えいの深刻さで決まります。ほかのすべての命令やネットワークの遅延が生むノイズに比べて、タイミングの漏えいの信号が強ければ、数回の測定で足りることがあります。そうでなければ、数百万回が必要になることもあります。タイミングの依存関係は、実行トレースや命令のタイミングの違いによって生じます。

### 定数時間の性質に違反するよくあるパターン

定数時間の性質に違反する、最もよくある 4 つのパターンは、次の 4 つのパターンに由来します。いずれも秘密データに依存しています。

```c
// 1. Conditional jumps
if(secret == 1):
{
...
}
while(secret > 0)
{
...
}

// 2. Array access 
lookup_table[secret];

// 3. Integer division (processor dependent) 
data = secret / m;

// 4. Shift operation (processor dependent)
data = a << secret;
```

秘密データを使う操作を行うコードを書くときは、これら 4 つのパターンを意識し、避けるようにしてください。

**条件ジャンプ**は、異なる命令が実行される結果になり、一般に 4 つのパターンの中で最も大きな時間差を生みます。プログラムの実行の流れを秘密データに依存させると、2 つの分岐がどれだけ違うかによって、非常に大きなタイミングの差が生じます。  

秘密データに依存する**配列アクセス**や、より一般的なメモリアクセスは、メモリ位置へのアクセス時のタイミングの差から、添字の値を取り出すのに使えます。このタイミングの差は、主にキャッシュの利用と、ある値がキャッシュ内にあるかどうかに由来します。秘密データに依存する置換テーブルを使う AES のような暗号は、[Cache-timing attacks on AES](https://cr.yp.to/antiforgery/cachetiming-20050414.pdf) で示されたように、ネットワーク越しでもこの攻撃の対象になります。

**整数の除算とシフト演算**は、除数やシフト量が秘密データに依存していると、秘密を漏らすことがあります。  
これらの演算は、使う CPU アーキテクチャやコンパイラによっては、秘密データを漏らすことがあります。

暗号アルゴリズムがこれらのパターンを必要とするために避けられない場合は、[マスキング技術](https://link.springer.com/chapter/10.1007/978-3-642-38348-9_9)を使って、実行時間と秘密データの相関をなくすか、小さくしてください。

次の節では、べき剰余に対するタイミング攻撃が、条件ジャンプをどのように悪用するかを説明します。

### 例: べき剰余に対するタイミング攻撃 {#example-modular-exponentiation-timing-attacks}

[Kocher](https://paulkocher.com/doc/TimingAttacks.pdf) は、べき剰余の計算に使うアルゴリズムが、タイミング攻撃を受けやすいことを示しました。
**RSA** や **Diffie-Hellman** のような広く使われている暗号システムはべき剰余を使うので、この脆弱性は重大なセキュリティ上のリスクになります。
たとえば RSA の復号では、暗号文 \(ct\) を秘密の指数 \(d\) でべき乗し、公開の法 \(N\) で割った余りを求めます。

$$
ct^{d} \mod{N}
$$

攻撃者が、同じ秘密の指数 \(d\) のもとで、さまざまな \(ct\) の値で復号関数に問い合わせられる場合、計算にかかった時間から \(d\) の値を推測できることがあります。
べき剰余は計算量が多く、広く使われているため、この演算を最適化すると性能が大きく上がります。
そのような最適化の 1 つが、*二乗によるべき乗*または*右から左への二進法*と呼ばれるもので、乗算の回数を \(\log{d}\) に減らします。

$$
\begin{flalign}
& \textbf{Input: } \text{base }y,\text{exponent } d=\{d_n,\cdots,d_0\}_2,\text{modulus } N \\
&r = 1 \\
&\textbf{for } i=|n| \text{ downto } 0: \\
&\quad\textbf{if } d_i == 1: \\
&\quad\quad r = r * y \mod{N} \\
&\quad y = y * y \mod{N} \\
&\textbf{return }r
\end{flalign}
$$

このコードは、指数のビット \(d_i\) によって分岐するため、前の節で説明した*条件ジャンプ*の原則に違反しています。
指数のビット \(d_i = 1\) のときは、余分な乗算 \(r = r * y\) が行われて実行時間が長くなり、その結果、\(d\) に含まれる 1 と 0 のビットの数が漏れます。
さらに、剰余乗算でよく使われる*モンゴメリ乗算*という手法は、定数時間ではなく、法と乗算の結果によって余分な計算を行います。
乗算の途中の値が法 \(N\) を超えると、還元のステップが必要になります。
この余分な還元のステップが、観測できるタイミングの差につながります。

これらのばらつきを悪用するために、攻撃者は次のような 2 つの入力 \(y\) と \(y'\) を作れます。

$$
\begin{align*}
y^2 < y^3 < N \\
y'^2 < N \leq y'^3
\end{align*}
$$

還元のない剰余乗算は \(t_1\) の時間がかかり、還元のステップが必要な剰余乗算は \(t_2\) の時間がかかるとします。
\(y\) では、2 回のモンゴメリ乗算のどちらにも還元のステップが不要なので、時間は \(t_1+t_1\) になります。
\(y'\) では、1 回目の乗算 \(r=r*r\) に還元は不要ですが、2 回目の \(r=r*y \) では必要になることがあり、その場合は余分に \(t_2\) の時間がかかります。

$$
\begin{flalign}
& \color{gray} \textbf{Input: } \text{base }y,\text{exponent } d=\{d_n,\cdots,d_0\}_2,\text{modulus } N \\
&\color{gray}r = 1 \\
&\color{gray}\textbf{for } i=|n| \text{ downto } 0: \\
&\color{gray}\quad\textbf{if } d_i == 1: \\
&\quad\quad r = r * y \mod{N}
\begin{cases}
    t_1,& \text{if } r * y < N\\
    t_2,& \text{if } r * y \geq N
\end{cases} \\
&\quad y = y * y \mod{N} \begin{cases}
    t_1,& \text{if } r * r < N\end{cases} \\
&\color{gray}\textbf{return }r
\end{flalign}
$$

分岐の挙動によって、タイミングの差が現れます。

|    | \(d_i = 0\)           | \(d_i = 1 \)                  |
|----|-----------------------|-------------------------------|
| \(y \) | \(t_1\) | \(t_1 + t_1\) |
| \(y'\) | \(t_1\) | \(t_1 + t_2\) |

このタイミングの差を解析すると、攻撃者は、特定のビット \(d_i\) が 0 か 1 かを推測できます。1 回の実行では十分な情報が得られないかもしれませんが、複数回の測定と統計解析を組み合わせれば、秘密鍵 \(d\) の復元に役立ちます。

## 定数時間解析ツール {#constant-time-tooling}

タイミング攻撃のリスクを緩和するには、暗号アルゴリズムを*定数時間*で実装する (実行時間が、入力にかかわらず一定である) のがベストプラクティスです。
そのようなタイミングの差がないことを確かめるために、暗号のコミュニティは、潜在的なタイミングの差を検出することを目的とした、さまざまなタイミング解析ツールを作ってきました。
これらのツールは、対象とするプログラミング言語 (たいていは C) と、タイミング解析の基本的なアプローチによって区別されます。
アプローチは、次の 4 つのカテゴリに分けられます。

1. **形式手法**
2. **シンボリック**
3. **動的**
4. **統計的**

どのアプローチにも、ほかと比べた長所と短所があります。

### 形式手法のツール

形式検証ツールは、与えられたモデルが、指定されたタイミング漏えいの性質を満たすことを、数学的に証明することを目的としています。
そのために、これらのツールはまず、ソースコードやバイナリを抽象化したもの (モデル) を作ります。
次に、モデルが違反してはならない性質を指定します。多くの場合、秘密のままにすべき変数やメモリ領域に注釈を付けます。
これらのツールは、元のコードを実行しないため、静的なツールに分類されます。

よく使われる形式手法のツールには、次のものがあります。

- [SideTrail](https://github.com/aws/s2n-tls/tree/main/tests/sidetrail)
- [ct-verif](https://github.com/imdea-software/verifying-constant-time)
- [FaCT](https://github.com/plsyssec/fact)

| 長所 | 短所 |
| :---- | :---- |
| **保証**: 形式検証は、解析したモデルのもとで、タイミングの漏えいがないことを証明する。 | **複雑さ**: これらのツールは、暗号と形式手法の両方で、より多くの専門知識を必要とする傾向があり、一般の開発者には使いにくい。 |
| **柔軟性**: 多くのツールが LLVM のバイトコードを使うため、さまざまな言語で使える。 | **モデル化と制約**: 形式化のときに置いた仮定が現実を完全には反映しておらず、検証が不完全になる可能性がある。たとえば、コンパイル段階で加わった変更によって、解析したモデルとは異なるバイナリになることがある。 |

### シンボリックツール

シンボリックツールは、シンボリック実行を使い、さまざまな実行経路やメモリアクセスが、シンボリック変数 (特に秘密データ) にどう依存するかを解析して、タイミングの漏えいを見つけます。
シンボリック実行は、ある性質に違反する具体的な値も示せるため、根本的な問題を理解するのに役立ちます。
シンボリック実行ツールの多くはキャッシュタイミング攻撃に焦点を当てているため、同じキャッシュを共有する攻撃者を想定した脅威モデルで役に立ちます。

よく使われるシンボリックツールには、次のものがあります。

- [Binsec](https://github.com/binsec/binsec)
- [pitchfork](https://github.com/PLSysSec/haybale-pitchfork)

| 長所 | 短所 |
| :---- | :---- |
| **反例**: シンボリック実行は、脆弱性の存在を示す具体的な反例やテストケースを提示でき、問題の理解と再現が楽になる。 | **時間がかかる**: シンボリック実行はあらゆる経路を探索するため、実行時間が長くなる。     |

### 動的ツール

動的ツールは、形式手法のツールと並んで、定数時間での実行を確かめる最も一般的な方法の 1 つです。これらのアプローチでは、通常、特定のメモリ領域を機密としてマークし、それがタイミングの情報を漏らさないことを確かめるか、実行の流れをトレースして、入力ごとの実行トレースの違いを検出します。

よく使われる動的ツールには、次のものがあります。

- [Memsan](https://clang.llvm.org/docs/MemorySanitizer.html): [チュートリアル](https://crocs-muni.github.io/ct-tools/tutorials/memsan)
- [TimeCop](https://www.post-apocalyptic-crypto.org/timecop/) / [Valgrind](https://neuromancer.sk/article/29)

| 長所 | 短所 |
| :---- | :---- |
| **きめ細かい解析**: 機密のメモリ領域を指定できるため、的を絞った解析に有効。 | **カバレッジが限られる**: テスト中に通った実行経路しか追跡できず、一部の脆弱性を見逃す可能性がある。 |
| **柔軟性**: コードベースのさまざまな部分に注釈を付けて、いろいろな状況に合わせられる。 |  |

### 統計的ツール

統計的ツールは、さまざまな入力でプログラムを実行し、経過時間を測って解析します。
すべての入力で時間の測定値が一貫していれば、タイミングの脆弱性がないことを示唆します。
これらのツールは、実際に実行されるコードを測るため、実用上の実装に近く、起こりうる変数も考慮に入ります。そのため、潜在的なタイミングの問題の最初の確認として優れています。

よく使われる統計的ツールには、次のものがあります。

- [dudect](https://github.com/oreparaz/dudect)
- [tlsfuzzer](https://github.com/tlsfuzzer/tlsfuzzer)

| 長所 | 短所 |
| -------- | ------- |
| **セットアップ**: 統計的なテストの設定はかなり簡単で、場合によっては、ソースコードにアクセスしなくてもできる。| **デバッグ**: タイミングの差が検出されても、統計的ツールは通常、問題の原因やコード内の場所についての情報を提供しない。 |
| **実用的**: 統計的ツールは実際の時間の漏えいを測るため、起こりうるすべての変数 (たとえば、コンパイラの最適化やアーキテクチャの違い) を含む、実環境の結果が得られる。 | **ノイズ**: 記録される測定値の品質は、テストハーネスが許す精度までしかない。コードのほかの部分がかなり長い時間を要する場合、タイミングの脆弱性が検出されないことがある。 |
