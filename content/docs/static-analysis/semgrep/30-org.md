# Semgrep を組織に導入する方法

Semgrep は、組織ごとの事情に合わせて柔軟に使えるように作られています。最良の結果を得るには、Semgrep の実行方法、使うルール、CI/CD パイプラインへの組み込み方を理解することが大切です。何から始めればよいか迷う場合は、
私たちがこれまでの経験から学んだことをもとにした、Semgrep を SDLC（ソフトウェア開発ライフサイクル）に最もうまく組み込む方法を見極めるための、7 段階の計画を使ってください。

## Semgrep の 7 段階の計画

1. 対応言語の一覧を見て、[Semgrep が役に立つか](https://semgrep.dev/docs/supported-languages/#language-maturity)を確かめます。

2. **探る**: 小さなプロジェクトで Semgrep を試し、効果を評価します。たとえば、プロジェクトのルートディレクトリに移動して、次を実行します。

    ``` shell
    semgrep --config auto
    ```

    このコマンドを実行するときは、いくつか注意点があります。

    - `--config auto` オプションは、メトリクスを Semgrep に送信します。望ましくない場合があります。
    - この方法で Semgrep を実行すると、検出された問題の概要（件数と重大度を含む）が表示されます。
      一般に、このコマンドラインフラグは、Semgrep が対応している技術の全体像をつかむのに使えます。
    - Semgrep は、ファイルの中身を解析するのではなく、拡張子でプログラミング言語を判断します。
      デフォルトの `.semgrepignore` ファイルにより、一部のパスはデフォルトでスキャンから除外されます。さらに Semgrep は、`.gitignore` ファイルに載っている未追跡のファイルも
      除外します。

3. **深く調べる**: auto オプションを使う代わりに、[Semgrep Registry](https://semgrep.dev/explore) から、主要なセキュリティパターンや、自分たちの技術スタックと要件に合ったルールセットを選びます。
   - 次を試します。

        ```shell
        semgrep --config p/default
        semgrep --config p/owasp-top-ten
        semgrep --config p/cwe-top-25
        ```

        あるいは、使っている技術に合わせてルールセットを選びます。

        ```shell
        semgrep --config p/javascript
        ```

   - まず、確信度が高く、影響が中程度または高いとメタデータに書かれているルールに注目します。結果が多すぎるときは、`--severity ERROR` フラグを使って、重大度が error のものだけに
   絞ります。
   - 見つかった問題を解決し、バグ報告には再現手順を含めます。

4. **微調整する**: 現在使っているルールセットの効果を見直して、理想的なルールセットの組み合わせを手に入れます。
   - ベストプラクティスのルールなど、セキュリティ以外のルールセットも見てみましょう。コードが読みやすくなり、将来の脆弱性の混入を防げる可能性があります。また、プロジェクトのほかの面も対象にすることを検討してください。
        - シェルスクリプト、設定ファイル、汎用ファイル、Dockerfile
        - サードパーティの依存関係（有料機能の Semgrep Supply Chain を使うと、脆弱なパッケージを悪用可能な形で使っていないかを検出できます）
   - Semgrep が誤って検出したコードパターンを無視するには、パターンに一致した行の直前の行（1 行目）にコメントを書きます。例: `// nosemgrep: go.lang.security.audit.xss`。あわせて、ルールを無効にすると決めた理由や、リスクを受け入れる理由も書いてください。
   - カスタマイズした `.semgrepignore` ファイルを作り、特定のファイルやフォルダを Semgrep のスキャンから除外して、ノイズを減らします。Semgrep はデフォルトで `.gitignore` に載っているファイルを無視します。これを維持するには、`.semgrepignore` ファイルを作ったあと、その `.semgrepignore` に、`:include .gitignore` というパターンで `.gitignore` を追加します。

5. 組織に固有のカスタム Semgrep ルールをまとめる、社内のリポジトリを作ります。
README ファイルには、Semgrep の短い使い方、リポジトリのカスタムルールの適用方法、カスタムルールの一覧表を載せます。また、貢献のチェックリストがあると、チームがルールの品質を保てます（[Trail of Bits の Semgrep ルール開発チェックリスト](https://github.com/trailofbits/semgrep-rules/blob/main/CONTRIBUTING.md#development-practices)を参照）。
社内の Semgrep リポジトリに新しいルールを追加するときは、誤検知と見逃しを減らすために、ピアレビューの手順を必ず設けてください。

6. **広める**: 開発者や関係するチームに、Semgrep を効果的に使う方法を教えます。
    - パイロットテストの結果を共有し、組織のコードの品質とセキュリティを改善するための助言を示します。
    Semgrep の限界（単一ファイルの解析しかできないこと）も示します。
    - 公式の学習リソース [Learn Semgrep](https://semgrep.dev/learn) を紹介し、ルールを簡単に作れる「シンプルモード」のある [Semgrep Playground](https://semgrep.dev/playground/new) を見せます。
    カスタムルールの書き方の概要を説明し、カスタムルールを書くのは簡単だと強調します。`fix:` キーを使って、カスタムルールに自動修正の機能を足せることも伝えます。脆弱性管理を支えるため、カスタムルールにメタデータ（CWE、確信度、可能性、影響など）を付けることを勧めます。
    開発者が「この問題のために Semgrep のルールを作るべきか」と考えるときは、次の質問が助けになります。
        - 特定のセキュリティ脆弱性を検出できるか。
        - ベストプラクティスや規約を徹底したり、コードの一貫性を保ったりできるか。
        - 性能に影響するコードパターンを検出して、コードを最適化できるか。
        - 特定のビジネス要件や制約を検証できるか。
        - 非推奨のコードや未使用のコードを見つけられるか。
        - 設定ファイルの設定ミスを見つけられるか。
        - コードをレビューするときに繰り返し出てくる問いか。
        - コードのドキュメントはどう扱われていて、ドキュメントの要件は何か。
    - チームが Semgrep について議論したり、カスタムルールを書いたり、問題を解決したりする場（Slack のチャンネルなど）と、Semgrep のルールのアイデアを書き留める場（Trello のボードなど）を用意します。また、組織のセキュリティ監査やバグバウンティプログラムで見つかったバグに対するカスタムルールを書くことも検討してください。チームが Semgrep を使うのに役立つ簡単なメモをまとめておくのもよい考えです（[元のブログ記事の付録](https://blog.trailofbits.com/2024/01/12/how-to-introduce-semgrep-to-your-organization/#:~:text=Appendix%3A%20Things%20I%20wish%20I%E2%80%99d%20known%20before%20I%20started%20using%20Semgrep)を参照）。
    - Semgrep Community Slack に注目してください。Semgrep のコミュニティが、問題の解決やカスタムルールの作成を手伝ってくれます。
    - Semgrep を使っていて見つけた既存の制限やバグは、GitHub の issue を立てて Semgrep のチームに報告するよう、チームに勧めます
    （Trail of Bits が出した[issue の例](https://github.com/semgrep/semgrep/issues/4587)を参照）。

7. 使っている CI ベンダーに関する Semgrep のドキュメントに目を通し、Semgrep を CI/CD パイプラインに実装します。開発者が大量の結果に圧倒されないよう、Semgrep は段階的に取り入れることが重要です。そこで、まず 1 つのリポジトリでパイロットテストを試します。次に、CI/CD パイプラインで、メインブランチに対して Semgrep の完全なスキャンを定期的に実行するようにします。最後に、イベント（プルリクエストやマージリクエストなど）が起きたときに、差分を対象にしたスキャンを加えます。
差分を対象にしたスキャンは、トリガー時にファイルの変更部分だけをスキャンするので、効率を保てます。この方法では、確信度が高く、真陽性になる結果を出す、微調整したルールのセットを調べるようにします。Semgrep の導入が成熟したら、CI/CD パイプラインで、未解決の Semgrep の検出結果がある PR のパイプラインをブロックするように設定します。

## 次は？ 組織での Semgrep の価値を最大にする

Semgrep を組織に導入するときは、頻繁に更新されることを覚えておいてください。その恩恵を最大限に受けるために、組織で 1 人を担当にして、新機能の分析（たとえば、Semgrep 独自のファイル単体のアプローチではなく、ファイルをまたぐコーディングパラダイムまでコードベースのスキャンを広げる Semgrep Pro など）、Semgrep のルールを置いた外部リポジトリについてのチームへの周知、有料サブスクリプション（プレミアムルールへのアクセスなど）の価値の見極めを任せましょう。
